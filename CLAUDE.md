# Chronologix AI

## What this is (today)
Chronologix AI ingests case documents (medical records, depositions, incident
reports, and eventually footage and audio) for personal injury and civil
litigation firms, and produces an organized, attorney-reviewed chronology,
summary, and inconsistency flags. The customer is small and mid-sized
plaintiff's firms that don't have a large in-house paralegal bench.

Phase 1 (current): text documents only — medical records, depositions,
incident reports. Phase 2+ (later, see PLANNING.md): video, audio, and
adjacent case types. Do not build phase 2 ingestion paths unless a task
explicitly says to; keep the document pipeline the priority until it's solid.

## Tech stack
FastAPI (Python 3.13) backend in `api/`, handling ingest/OCR/chunking and
all LLM calls. Next.js (TypeScript, App Router) frontend in `web/` for the
attorney review UI. Supabase (Postgres + pgvector, Auth, Storage) for data.
Anthropic Claude for chronology generation/summarization; Voyage AI
(`voyage-3`) for chunk embeddings.

## Architecture (one paragraph, not a tour)
Attorneys upload case documents through the `web/` Next.js UI; files land in
Supabase Storage. The `api/` FastAPI service OCRs and chunks each document
(`ingest/`), extracts dates/entities (`extraction/`), and stores chunks with
embeddings in Postgres/pgvector. Phase 2 adds video/audio via `evidence/`
(Deepgram transcription) with the same shape. `chronology/` queries
chunks/segments in date order and calls Claude to build the chronology;
`flags/` cross-checks for inconsistencies; `demands/` (Phase 3) drafts a
demand letter from a signed-off chronology. These three are the only
modules allowed to call an LLM (see `docs/architecture.md`) — the
centralization keeps every "generate a claim/document about a case" path
under `accuracy-verifier`'s scrutiny. `web/` reads finished output from
the API for attorney review, edit, and sign-off; nothing in `web/` talks
to the LLM or Supabase directly.

## Domain vocabulary
- **Chronology**: the date-ordered timeline of events built from a case's
  documents. This is the core deliverable — treat bugs here as high severity.
- **Source document**: any uploaded record (medical record, deposition,
  report). Every fact in a chronology must trace back to one.
- **Flag**: an automatically detected inconsistency (conflicting dates,
  contradicting statements) surfaced for attorney review, never resolved
  silently by the system.
- **Attorney sign-off**: the human review step before a chronology leaves
  draft status. Nothing generated by an agent is considered final without it.

## Compliance and data handling (non-negotiable)
- Case documents contain PHI and privileged material. Treat every file
  under `/sample-data`, `/fixtures`, or any ingest directory as sensitive
  by default, even if it looks like a test file.
- Never commit real client data, even accidentally. Sample/test data must
  be synthetic — if you're not sure a fixture is synthetic, ask before
  using it in a test.
- Don't log full document contents in application logs. Log document IDs,
  not contents.
- Flag anything that looks like it would need a BAA (Business Associate
  Agreement) with a vendor before you wire up a new third-party API or MCP
  server that will touch case documents.

## Working agreements
- Work autonomously through planned phases/sub-projects without pausing for
  approval between them: design briefly, plan, delegate implementation to
  `builder`, verify with `code-reviewer`/`accuracy-verifier`, commit, move on.
  Don't ask "should I continue" — check in only for: missing credentials or
  other hard blockers, a business/legal decision explicitly flagged as
  needing deliberate human input (e.g. PLANNING.md's defense-side question,
  now decided: plaintiff-side only, do not build a defense lane),
  or an action that's costly/destructive/hard to reverse. Everything else,
  make the call and keep moving; report what shipped when it's done.
- **Unit tests are the floor, not the proof. Live-verify anything that
  touches an LLM, an external API, or the browser.** A full green mock suite
  has repeatedly hidden broken real integrations (Claude wrapping JSON in
  markdown fences, a dropped material fact, missing CORS, an unset
  credential). Mocks return clean data by construction. Run the real thing
  end to end, and run `accuracy-verifier` on chronology/flag/demand output
  against known ground truth. Full detail in `docs/RETROSPECTIVE.md`.
- **Model-tier orchestration** (keep this split): the orchestrator handles
  design, decomposition, safety-critical judgment, review adjudication, and
  inline accuracy checks; delegate implementation to a cheaper `builder`
  (cheapest tier when handed complete code, mid-tier for prose-described
  work); reviews run on a mid-tier `code-reviewer`; reserve the strongest
  model for `accuracy-verifier` and genuine factual judgment. Builders never
  run `git` — the orchestrator commits, sequentially, to avoid concurrent
  writes to the shared index.
- **Before dispatching a review, verify the commit's real parent** with
  `git log --oneline` and hand the reviewer the correct `parent..HEAD` range.
  A wrong parent produces false-positive "scope creep" findings.
- **Verify a new dependency actually installs and imports on this machine
  before designing around it.** LiteLLM and `unstructured` were both chosen
  then abandoned (no Windows wheel / too heavy). Prefer libs with prebuilt
  Windows wheels. Windows gotchas (Tesseract via winget, `taskkill` not
  `pkill`, `tr` not `${//}` for backslashes, scratchpad not `/tmp`) are in
  `docs/RETROSPECTIVE.md`.
- Plan before implementing on anything non-trivial. See `/ship` skill and
  `prompts/orchestrator-prompt.md`.
- Route verbose, disposable work (log digging, broad codebase search,
  dependency audits) to a subagent instead of doing it in the main
  conversation. See `.claude/agents/`.
- Every change to how a chronology is generated, ordered, or summarized
  must pass both `code-reviewer` and `accuracy-verifier` before it's
  considered done. A code review pass alone does not clear this bar.
- Prefer cheaper models for read-only, high-volume work (log scanning,
  file search) and reserve the strongest model for the accuracy-verifier
  and for actual chronology-generation logic. See `cost-auditor`.
- If this project has Graphify installed (`graphify build .`), query the
  project graph for "what depends on X" / "what calls Y" style questions
  instead of grepping or reading files cold. Rebuild the graph after any
  session with substantial structural changes.
- When Claude gets something wrong more than once — a wrong path, a
  misunderstood convention — add the correction to this file instead of
  just fixing it and moving on.

## What NOT to do
- Don't add footage/audio ingestion, new case-type verticals, or
  demand-letter drafting unless PLANNING.md's current phase says so.
- Don't let an agent mark its own work reviewed. Review must come from
  the `code-reviewer` or `accuracy-verifier` subagent, not from the agent
  that wrote the code.
- Don't silently "fix" a flagged inconsistency in source data. Flags are
  surfaced to attorneys, not resolved by the system.
